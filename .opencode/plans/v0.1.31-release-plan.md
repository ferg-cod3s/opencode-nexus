# OpenCode Nexus v0.1.31 Release — Implementation Plan

## Context

**Goal:** Take OpenCode Nexus from its current "half-built, one IPA shipped" state to a TestFlight build that's actually worth handing to beta testers. This means: fix the app first (Phases 0–4), then operationalize the beta program around it (Phase 5).

**Why now:** The repo has three independent problems that all block a useful release:
1. **Security:** 4 committed Apple signing secrets in git history.
2. **Architecture:** ~6,600 LOC of Rust backend that duplicates `@opencode-ai/sdk`, plus 3 legacy Astro pages calling 19 ghost commands. iOS builds slowly, runtime fails silently.
3. **Beta plumbing:** Build 30 was uploaded Nov 14 2025, but version derivation in `scripts/build-ios-archive.sh` would now produce build 2 — App Store Connect will reject the next upload (`CFBundleVersion` must increase monotonically). No dSYM upload to Sentry, so native panics from TestFlight devices arrive unsymbolicated. No in-app feedback path, no release runbook, no smoke test.

**Strategy:** Phases 0–4 make the app worth shipping. Phase 5 makes the beta program work. Order matters — adding a feedback button to a settings page slated for quarantine in Phase 2 would be wasted work.

**Current state vs. claims (verified by file inspection):** `status_docs/TODO.md` and `CLAUDE.md` both claim SDK Phase 2 deleted `api_client.rs` (399 LOC), `chat_client.rs` (342 LOC), and `message_stream.rs`. **All three files still exist** and are imported by `lib.rs:23-40`. Treat in-repo status docs as aspirational; this plan works from observed file state.

**Non-goals for this release:** Android, PWA, file upload, QR setup, sync controls, public App Store submission, native E2E in CI (deferred — covered by P6 manual smoke test).

### P5.1 — dSYM upload to Sentry

**Why:** Native Rust panics from TestFlight devices arrive in Sentry as raw addresses without symbolication. App Store Connect symbol upload (`uploadSymbols=true` in ExportOptions.plist) is a *different* pipeline; it does not feed Sentry.

**Steps:**
1. Create new Sentry org-level auth token (scope: `project:releases`); add to GitHub Secrets as `SENTRY_AUTH_TOKEN`. Also add `SENTRY_ORG`, `SENTRY_PROJECT`.
2. Write `scripts/upload-dsyms-sentry.sh`:
   ```bash
   #!/usr/bin/env bash
   set -euo pipefail
   ARCHIVE_PATH="${1:?path to .xcarchive}"
   sentry-cli upload-dif --org "$SENTRY_ORG" --project "$SENTRY_PROJECT" \
     --include-sources "$ARCHIVE_PATH/dSYMs"
   ```
3. Insert into `.github/workflows/ios-release.yml` between "Build & Archive" and "Upload to TestFlight":
   ```yaml
   - name: Upload dSYMs to Sentry
     env:
       SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
       SENTRY_ORG: ${{ secrets.SENTRY_ORG }}
       SENTRY_PROJECT: ${{ secrets.SENTRY_PROJECT }}
     run: ./scripts/upload-dsyms-sentry.sh build/OpenCodeNexus.xcarchive
   ```
4. Install `sentry-cli` on the self-hosted runner if not already present (`brew install getsentry/tools/sentry-cli`).

**Verification:** After the next CI build, force a Rust panic from a debug build (or cause a `unwrap()` failure on an unused code path) → confirm symbolicated frames appear in Sentry within 5 minutes.

## Phase ordering rationale (why not Phase 5 first?)

Three things make sequencing matter:
1. **Feedback button before Phase 2 = wasted work.** Phase 2 quarantines `settings.astro`. Adding a feedback row there now means redoing it after Phase 2 changes the page structure.
2. **dSYM upload before Phase 2 = symbolicating dead code.** Phase 2 deletes 6,600 LOC of Rust. Sentry's symbol cache for those addresses becomes garbage.
3. **Beta program before Phase 1 = guaranteed rejection.** App Store Connect rejects build 31 if `package.json` still says `0.0.0-dev002` (script derives build 2).

If a beta build is genuinely needed *now* (before Phases 0–4), only the Phase 1 monotonic version fix is mandatory. Skipping the rest means testers receive a build with committed secrets in git, broken legacy pages, and no UI polish — defeating the purpose of testing.
