# Release Plan Handling Plan

## Overview
This plan outlines the recommended approach to handle the RELEASE-PLAN.md for releasing OpenCode Nexus as a mobile-first Tauri 2 client for iOS (TestFlight) and other platforms, based on research and analysis of the current repository state.

Each phase includes a specification that would be produced by running `/ai-eng/specify` for that phase.

## Phase 0: Security & Cleanup Specification
**Specification for:** Security & Cleanup (1-2 days)

**Objective:** Eliminate security risks from committed secrets and reduce repository noise to improve maintainability.

**Requirements:**
- **Must-have:**
  - Remove all committed signing/test secret files from git history (after rotation/revocation)
  - Update .gitignore to prevent future accidental commitment of secrets
  - Archive non-essential root markdown files and consolidate iOS build scripts
  - Remove dead JavaScript files that are no longer used
- **Nice-to-have:**
  - Create documentation explaining the cleanup process for future contributors
  - Verify no personal data or sensitive information remains in commit history

**Acceptance Criteria:**
- `git ls-files | grep -E '\.(p8|pem|mobileprovision|p12)$'` returns no results
- `.gitignore` contains patterns to ignore `*.p8`, `*.pem`, `*.mobileprovision`, `*.p12`, `.env.*`
- Root directory contains fewer than 10 non-essential files (README, license, etc.)
- `frontend/src/chat.js` and `frontend/src/login.js` are removed
- ~66 root markdown files moved to `docs/archive/sessions/`
- ~39 root iOS scripts consolidated into `scripts/build-ios.sh`

**Output Deliverables:**
- Updated .gitignore file
- Cleaned repository with secrets removed from tracking
- Archived session documentation in `docs/archive/sessions/`
- Consolidated iOS build script at `scripts/build-ios.sh`
- Commit log showing removal of secret files (after rotation/revocation)

## Phase 2: Rust Backend Simplification Specification
**Specification for:** Rust Backend Simplification (2-3 days)

**Objective:** Reduce Rust backend to only essential connection persistence and logging functions, leveraging the frontend @opencode-ai/sdk for all chat/session/streaming/model operations.

**Requirements:**
- **Must-have:**
  - Frontend chat/session/streaming/model operations must use @opencode-ai/sdk exclusively
  - Rust backend must only expose connection persistence/lifecycle and logging commands
  - Legacy frontend pages invoking unregistered Rust commands must be quarantined or stubbed
  - All removed Rust modules and their associated tests must be deleted
  - Cargo.toml must reflect removed dependencies
- **Nice-to-have:**
  - Create diagram showing frontend/backend communication boundaries
  - Document the SDK-to-Tauri interface contract

**Acceptance Criteria:**
- Frontend invokes only these Rust commands via `invoke()`:
  - connect_to_server
  - test_server_connection
  - get_connection_status
  - get_current_connection
  - disconnect_from_server
  - get_saved_connections
  - save_connection
  - get_last_used_connection
  - get_application_logs
  - log_frontend_error
  - clear_application_logs
- src-tauri/src/lib.rs contains only handlers for the above 10 commands
- Modules api_client.rs, chat_client.rs, connection_manager.rs, event_bridge.rs, model_manager.rs, session_manager.rs, streaming_client.rs, chat_client_example.rs are deleted
- Associated test files for deleted modules are removed
- Cargo.toml removed tokio, reqwest, futures, sysinfo, sentry, and other unused dependencies
- `cargo test` passes
- Frontend unit tests pass
- Manual testing confirms chat, session management, and model selection work via SDK

**Output Deliverables:**
- Minimized src-tauri/src/lib.rs with only connection/log command handlers
- Deleted Rust module files
- Updated Cargo.toml
- Quarantined or stubbed legacy frontend pages (/settings, /test-chat, /dashboard, /chat logout)
- Test suite confirmation (cargo test + bun test)

## Phase 3: iOS Build & Release Verification Specification
**Specification for:** iOS Build & Release Verification (2-3 days)

**Objective:** Ensure the iOS build works correctly and can be prepared for TestFlight distribution.

**Requirements:**
- **Must-have:**
  - iOS simulator builds successfully
  - iOS device release build produces valid IPA
  - IPA contains correct bundle identifier, version, and entitlements
  - ExportOptions.plist is configured for app-store distribution
  - No hosted macOS runners are used in the build process (self-hosted only)
- **Nice-to-have:**
  - Automated TestFlight upload script using App Store Connect API keys (stored securely in CI)
  - Documentation of the iOS release process for team reference

**Acceptance Criteria:**
- `bun run tauri ios dev` succeeds in simulator
- `bun run tauri ios build --release` succeeds and produces IPA
- IPA validation confirms:
  - Bundle identifier: `com.agentic-codeflow.opencode-nexus`
  - Version: 0.1.0 (with incremented build number)
  - Entitlements match src-tauri/ios-config/src-tauri_iOS.entitlements
  - ExportOptions.plist method = "app-store"
- Build process uses only self-hosted macOS runner (verified via build logs or CI configuration)
- No build errors related to version mismatches or signing configuration

**Output Deliverables:**
- Successful simulator build logs
- Valid IPA file from `bun run tauri ios build --release`
- IPA validation results (using security and plutil tools)
- Optional: TestFlight upload script
- Build process verification showing self-hosted runner usage

## Phase 4: Mobile UI Polish & Final Validation Specification
**Specification for:** Mobile UI Polish & Final Validation (3-5 days)

**Objective:** Ensure the mobile application meets quality standards for touch interactions, visual polish, and overall stability before release.

**Requirements:**
- **Must-have:**
  - All touch targets meet minimum 44px requirement
  - Proper safe area handling for iPhone notch, home indicator, and rounded corners
  - Splash screen and proper iOS icon set implemented
  - PWA components removed if present
  - Application functions correctly on physical iOS device
  - Full test suite passes (backend, frontend, linting, typechecking)
- **Nice-to-have:**
  - Accessibility audit (WCAG 2.1 AA) for critical user flows
  - Performance profiling on device (launch time, memory usage, responsiveness)
  - User acceptance testing with internal stakeholders

**Acceptance Criteria:**
- Manual verification confirms touch targets ≥44px in chat interface, settings, etc.
- Safe area handling prevents content from being obscured by notch/home indicator
- Splash screen appears on launch
- Proper iOS icon set visible in Settings → General → About and on home screen
- No PWA registration or installation prompts appear
- Physical device testing confirms:
  - Chat interface functional with real SDK connection
  - Session management (create, list, switch) works
  - Model selector displays and persists selections
  - Offline indicator behaves appropriately
- `cargo test` passes
- `cd frontend && bun test` passes
- `bun run lint` passes
- `bun run typecheck` passes

**Output Deliverables:**
- Touch target verification documentation/screenshots
- Safe area handling verification
- Splash screen and icon set in Xcode project
- Physical device test results
- Complete test suite pass confirmation
- Optional: accessibility and performance reports

## Risks & Mitigations (Applicable to All Phases)
- **Risk:** Legacy frontend pages may break if stubbed incorrectly.  
  **Mitigation:** Keep stubs minimal and verify navigation does not crash; consider removing routes entirely if not needed for MVP.
- **Risk:** Removing Rust backend modules may break hidden invocations.  
  **Mitigation:** Before deletion, audit all frontend invoke() calls; ensure only the retained commands are used.
- **Risk:** iOS signing/config mismatches persist.  
  **Mitigation:** Use `bun run tauri ios init` or manual copy from ios-config to regenerate project; verify with Xcode.
- **Risk:** Version drift between files.  
  **Mitigation:** Automate version bump via script in CI; enforce via pre-commit hook if desired.
- **Risk:** Physical device testing reveals UI/UX issues.  
  **Mitigation:** Allocate sufficient time in Phase 4 for iterative fixes based on device testing.
